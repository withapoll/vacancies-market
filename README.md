# Рынок data-вакансий

Учебный проект для DE-портфолио: сбор выборки data-вакансий из API, накопление истории в PostgreSQL и аналитические витрины в dbt. Airflow подключается после работающего сквозного процесса.

Первая версия — один источник, роли Data Engineer и Data Analyst и две витрины. Кандидат на источник — «Работа России»; первые ответы API получены, контракт данных и пагинация ещё проверяются. Выводы будут относиться к собранной выборке, а не ко всему рынку.

## Что уже есть

- PostgreSQL 16 в Docker Compose.
- Миграции raw-слоя: попытки сбора, журнал поисковых запросов и наблюдения вакансий.
- Зависимости Python и набросок сборщика.

Сборщик, регулярное накопление истории, dbt, Airflow и CI пока не реализованы. Рабочий план и заметки для интервью хранятся локально в `PLAN.md` и `INTERVIEW.md` и не входят в репозиторий.

## Локальный запуск базы

Команды для PowerShell из корня проекта:

```powershell
docker compose up -d db
docker compose exec -T db psql -U postgres -d vacancies
```

База доступна на `localhost:5434`, имя базы и пользователь — `vacancies` и `postgres`. Пароль для локальной разработки указан в `docker-compose.yml`. Пример строки подключения Python — в `.env.example`; значения нужно заменить на локальные.

При первом запуске с пустым томом PostgreSQL выполняет файлы из `sql/migrations` по порядку. При существующем томе новые миграции автоматически не применяются. Для базы, где уже выполнена только `001_raw.sql`:

```powershell
docker compose exec -T db psql -U postgres -d vacancies -v ON_ERROR_STOP=1 -f /docker-entrypoint-initdb.d/002_collection_runs.sql
```

Миграцию `002` нужно выполнить один раз. Она рассчитана на пустые старые таблицы и остановится, если найдёт записи. Удалять том для обновления схемы не нужно.

Проверка ограничений и выбора принятого среза после миграции:

```powershell
Get-Content -LiteralPath sql/tests/raw_contract.sql -Raw -Encoding UTF8 | docker compose exec -T db psql -U postgres -d vacancies -v ON_ERROR_STOP=1
```

Проверка завершается сообщением `Raw contract checks passed`. Тестовые строки откатываются транзакцией; значения identity-последовательностей при откате не возвращаются, поэтому пропуски в `id` нормальны.

## Как хранится история

- `raw.collection_runs` — одна попытка обойти все выбранные поисковые запросы. Хранит список запросов, источник, день среза, время начала и окончания, статус и причину ошибки.
- `raw.collection_log` — ход отдельного запроса внутри попытки: сколько сообщил источник, сколько получено записей и сколько страниц завершились ошибкой. Число полученных записей может включать дубли.
- `raw.vacancies` — одна вакансия источника в одной попытке. Повторные попадания по разным запросам объединяются по идентификатору вакансии; новая попытка хранит свои наблюдения отдельно.
- `raw.accepted_runs` — последний по времени начала успешный запуск каждого источника за день. При одинаковом времени используется больший `id`.
- `raw.accepted_vacancies` — наблюдения из этих запусков; будущие модели dbt должны читать этот view.

`snapshot_date` — день начала сбора по `Europe/Moscow`. `started_at` и `finished_at` относятся к запуску, `observed_at` — к получению конкретной вакансии, `loaded_at` — к её записи в БД. Дата публикации источника хранится отдельно в payload. Сбор через полночь относится к дню начала и не является точным состоянием рынка на один момент времени.

### Договорённость для будущего сборщика

1. Создать запуск со статусом `running` и зафиксированным списком запросов, затем строки журнала для этих запросов.
2. Получать страницы, удалять контактные поля до записи и логирования, сохранять наблюдения. При повторном попадании вакансии в рамках запуска оставлять первое полученное наблюдение.
3. После исчерпания ретраев пометить запрос и весь запуск как `failed`. Частичные данные можно сохранить для диагностики, но в принятый срез они не входят.
4. Только после обхода всех запланированных запросов и страниц, сохранения данных и проверки журналов перевести запуск в `complete`. Финальную запись данных и изменение статуса выполнить в одной транзакции.

Схема проверяет ключи, связи, статусы и согласованность времени окончания. Полноту обхода проверяет сборщик: сама БД не знает, все ли страницы API прочитаны. Нулевой результат допустим при подтверждённом успешном обходе. Оборванный процесс может оставить `running`; такой запуск тоже исключён из витрин.

Повтор за тот же день создаёт новую попытку. Успешный повтор заменяет принятый срез в представлениях, не удаляя предыдущие данные; неуспешный его не меняет. Число сырых строк при повторах растёт намеренно, но в принятом срезе одна вакансия учитывается один раз. Сбор текущего состояния нельзя выдавать за восстановление пропущенного дня.

## Что дальше

Проверить API, составить обезличенный пример ответа и контракт данных. После этого — сборщик и регулярное накопление истории, затем dbt, витрины, Airflow и CI.

Несколько источников, сопоставление компаний, анализ исчезновения вакансий и конвертация валют остаются на развитие после первой версии.
